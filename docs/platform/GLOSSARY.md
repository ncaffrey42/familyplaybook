# Glossary

Canonical product terms, cross-referenced against what the code actually
calls them. Where they diverge, the divergence is recorded on purpose —
this is the file that answers a diligence team's "why does the schema say
one thing and the app say another" before they have to ask.

Every architecture prompt should use the **Canonical term** column when
writing docs, and add a row here the first time it introduces or renames a
concept.

## Core content model

| Canonical term | What it means | Code / schema reality | Notes |
|---|---|---|---|
| **Playbook** | **The complete content of exactly one workspace**: every `guides` and `packs` row sharing that `workspace_id`, plus the `pack_guides` edges between them. One workspace ⟺ one playbook. | **Not a table, and deliberately never will be** — `workspace_id` *is* the playbook pointer (`CONTENT_ENGINE.md` §4). Today, pre-tenancy, it degenerates to "the sum of one user's `guides` + `packs`", which is the same set via `ARCHITECTURE.md` §3.1's bijection. | **Formalized by Prompt 4.** A `playbooks` table would carry no information `workspace_id` doesn't already carry. Ask "where is the playbook in the schema?" and the answer is "the `workspace_id` equivalence class". Prompt 9's *per-property playbook* is a sub-tree (one bundle) of a host workspace's playbook, not a competing root. |
| **Guide** | One how-to: a named set of ordered steps (e.g. "How to turn off the water"). | Table `public.guides`. Steps live in a `steps jsonb` column (each step: `text`, `image_url`, `video_url`). | Code and product agree here — no drift. Post-tenancy, a guide belongs to a **workspace**; `guides.user_id` remains as **provenance** (who authored it), no longer as the authorization key (`CONTENT_ENGINE.md` §2.2). |
| **Category** | The vertical-specific bucket a guide falls into — family: How To / Find It / Reference (/ Emergency); host: Arrival / House / Local / Departure. | `guides.category`, unconstrained nullable `text`. **Designed by Prompt 4**: a `content_categories (workspace_type, key, label, prompt_hint, …)` lookup table, not yet migrated. | Stored values are the literal display strings (`'How To'`, not `'how_to'`) — see `CONTENT_ENGINE.md` §3.3. Currently hardcoded in six places which have **already drifted**: `GuideIcon.jsx` styles an `Emergency` category that no picker, filter chip, or AI enum knows about. |
| **Bundle** | A named, ordered collection of guides (e.g. "New Babysitter" bundle). The product-facing name. | Table `public.packs`; join table `public.pack_guides`; functions `is_pack_editable()`, `get_pack_guide_counts()`. Some newer code paths (`viewer_can_see_bundle()`, RPC output field `'bundle'` in `get_shared_content`) already say "bundle." | **Known drift.** DB tables, several functions, some routes (`src/pages/packs/`, `AddGuidesToPackModal.jsx`) and the entitlement key `bundles_max` say `pack`/`bundles_max` interchangeably. The frontend has *both* `src/pages/packs/` and `src/pages/bundles/`, and both `AddGuidesToPackModal.jsx` and `AddGuidesToBundleModal.jsx` exist side by side. Do not rename the tables opportunistically — record any rename as a `DECISIONS.md` entry with a migration plan, since `packs`/`pack_id` is a foreign key target across `pack_guides`, `share_grants`, `shared_links`, and RLS functions. |
| **Library** | Anthropic-curated (i.e. app-provided, not user-authored) starter guides/bundles a user can copy into their own playbook. | Tables `public.library_guides`, `public.library_packs`. | `library_pack_id` is text (a slug), not a UUID FK to `packs` — libraries are a separate, non-tenant-scoped catalog, not user content. |
| **Handoff bundle** | An AI-assembled, purpose-built bundle generated on demand (e.g. "assemble everything a babysitter needs tonight"), distinct from a bundle a user builds by hand. | `src/components/HandoffAssembleSheet.jsx`; edge function `assemble-handoff-bundle`. | A *behavior* (AI assembly), not a separate schema entity — it produces an ordinary bundle. |

## Sharing & access

| Canonical term | What it means | Code / schema reality | Notes |
|---|---|---|---|
| **Share link** | An unguessable public URL to one guide or bundle, optionally with an expiry, requiring no login to view. | Table `public.shared_links`; resolved via the `get_shared_content()` `SECURITY DEFINER` RPC. | See `DECISIONS.md` for why resolution is RPC-only. |
| **Share grant** | An owner giving one specific guide or bundle to one specific accepted family member — narrower than family sharing's "see everything." | Table `public.share_grants`, FK'd to `family_invitations`; enforced by `viewer_can_see_guide()` / `viewer_can_see_bundle()`. | Distinct from a share link: a grant requires the recipient to already be an accepted family member; a share link requires nothing. Under the Prompt 3 model, grants are the **narrowing axis** that composes with (never replaces) coarse workspace-wide **capabilities** — which is how the host **Cleaner** reuses this exact mechanism. **Dormant in production**: no code path creates one today (see Helper). |
| **Helper** | The read-only role: a family member with `viewer` role, and — separately — the name for the public, unauthenticated experience of opening a share link at all. | `family_invitations.role = 'viewer'`, enforced via `is_accepted_family_member(owner_id, 'viewer')`. Also: `PublicSharePage.jsx` comment — *"Helper mode — the read-only guest view of a shared guide or bundle."* | **Two related but distinct uses of "Helper."** (1) A signed-in family member with viewer role. (2) The anonymous "Helper mode" UI shown on any opened share link (no tab bar, nothing editable), regardless of whether the visitor is a family member. Keep both senses when writing docs; disambiguate as "Helper (role)" vs "Helper mode (surface)" if a doc needs both in the same paragraph. **Sense (1) is fully built but unreachable** — both invite call sites hardcode `role: 'editor'` and there is no role picker, so no viewer invitation, and therefore no share grant, is ever created (`RBAC.md` §7). |
| **Guest** | The host-vertical visitor — someone who opens a property's guest guide link with no account and no ongoing relationship to the owner, as opposed to a family "Helper" who has an accepted, durable invitation. | Not a schema role, and **deliberately never will be** (`RBAC.md` §1.2, §9). Referenced today only in host-mode UI copy (`HostMode.jsx`). | **Resolved by Prompt 3:** "guest" names an *access path*, not a role — never a `workspace_members` row, never a role value, never an RLS subject. Guest access is exclusively `get_shared_content()`. The schema has zero `TO anon` policies today, and keeping it that way is what makes "a guest must never enumerate" a structural guarantee rather than a policy promise. |
| **Capability** | A single permitted action, named `<resource>.<verb>` (e.g. `content.edit`, `share.grant.manage`, `billing.manage`). What roles are composed of. | **Designed by Prompt 3** (`RBAC.md` §2–3), not yet migrated — the `capabilities` catalog + `workspace_role_capabilities` matrix, read through one `has_capability(workspace_id, capability)` `SECURITY DEFINER` helper. | Permissions are **rows, not code**: a new vertical or a changed role is an `INSERT`. Capabilities are workspace-wide and coarse; **share grants** narrow them per-person, per-item — two different axes that compose, neither replacing the other. |
| **Role** | A named bundle of capabilities, scoped to one vertical: family — `owner`, `editor` (**Adult**), `viewer` (**Helper**); host — `owner`, `manager`, `cleaner`. | **Designed by Prompt 3** — `workspace_roles (workspace_type, role, label)`. Stored values stay `owner`/`editor`/`viewer` (unchanged from `family_invitations.role`); product labels live in `workspace_roles.label`. | Don't rename the stored values — `ARCHITECTURE.md` §3.3's sync trigger copies `family_invitations.role` straight into `workspace_members.role`. "Adult" and "Helper" are labels over `editor` and `viewer`, not new values. |
| **Family** | The default, existing vertical/workspace type: a household sharing one playbook. | Implicit today (see `TENANCY.md` — there is no `workspace_type` column yet); the term appears throughout as the product name for the B2C audience. | Becomes `workspace_type = 'family'` once tenancy lands (Prompt 1). |

## Billing & entitlements

| Canonical term | What it means | Code / schema reality | Notes |
|---|---|---|---|
| **Plan** | What a user (or, later, an org) is subscribed to; drives feature limits. | Tables `public.plans`, `public.plan_entitlements`; `plan_key` column on `user_billing`. | |
| **Entitlement** | A specific numeric or boolean capability tied to a plan (e.g. `active_guides_max`, `bundles_max`, `ai_generation`). | `public.plan_entitlements` rows, `feature_key` column; read via `get_user_numeric_limit()`. | Entitlement key `bundles_max` governs the `packs` table — see the Bundle/pack drift note above. |
| **Read-only-over-limit** | When a downgrade puts a user over their plan's item limit, the oldest-by-`updated_at` excess items become RLS-enforced read-only — never deleted, never archived. | `is_guide_editable()`, `is_pack_editable()`; `supabase/migrations/20240103_readonly_tier_enforcement.sql`, `20240104_retire_archive.sql`. | The **archive** feature (`is_archived`/`archived_at` columns) is retired in favor of this model; the columns remain only for backward-compat reads. Don't reintroduce "archive" language in new UI — the canonical term is "read-only." |

## Tenancy (designed, not yet applied — see `TENANCY.md`, `ARCHITECTURE.md`)

| Canonical term | What it means | Code / schema reality | Notes |
|---|---|---|---|
| **Organization** | The billing + identity boundary above a user; can contain multiple workspaces. | **Designed by Prompt 1** (`docs/platform/ARCHITECTURE.md` §2.1), not yet migrated. Today the string only appears as a generic variable/component name (`HeartMark.jsx`), unrelated to this meaning. | Every existing user backfills to one personal `organizations` row (`is_personal = true`). No billing relationship yet — `user_billing` stays user-keyed until Prompt 17. |
| **Workspace** | The content boundary; what a "playbook" belongs to going forward. One org has many, discriminated by `workspace_type`. | **Designed by Prompt 1** (`ARCHITECTURE.md` §2.2), not yet migrated. `AuthCallback.jsx` uses "workspace" only as incidental wording today, not a schema concept. | Existing users backfill to one personal `family` workspace. `workspace_type` is `text` + `CHECK`, not a native enum — matches the schema's existing convention (`plan_key`, `billing_provider`, `role`, `status`, `kind`) so a new vertical is an additive `CHECK` edit, not a restructure. |
| **Workspace member** | A user with a settled role (`owner`/`editor`/`viewer`) inside one workspace. | **Designed by Prompt 1** (`ARCHITECTURE.md` §2.3), not yet migrated — the `workspace_members` table. | Distinct from an *invitation*: `family_invitations` (pending token, decline history) stays the invite workflow; a sync trigger projects accepted/declined/removed rows into `workspace_members`. Role vocabulary is a placeholder, value-preserving copy of today's `family_invitations.role` — the real RBAC matrix (including `helper`, `guest`) is Prompt 3's job. |
| **Property** | A host workspace's unit of guest-facing content — one short-term-rental listing, with its own guest guide playbook. | **Built by Prompt 9** (unapplied): table `public.properties` in migration `20240130` — a thin veneer (name, address, photo) over `bundle_id NOT NULL UNIQUE → packs`. | The one-bundle-per-property convention is enforced by the schema (`UNIQUE`), not prose. `ON DELETE RESTRICT` means content outlives the veneer. Everything built for bundles — share links, expiry, QR, Ask the Playbook — works on properties with zero new code. |
| **Host Starter Kit** | Ten ready-made, fill-in-the-blank host guides (wifi, check-in, check-out, parking, appliances, house rules, local picks, trash, emergencies, "Just ask") an owner copies and edits to reach a complete playbook in minutes. | **Seeded by Prompt 9** (unapplied): `library_packs` row `pack_host_starter` + ten `library_guides` rows in migration `20240131`, flowing through the existing `handleAddBundleFromLibrary` copy-to-mine path. | Library rows, not code — editable without deploys, and the copy flow already handles entitlements and `template_id` provenance. Library tables are world-readable; nothing sensitive belongs in seed content. |
| **Ask the Playbook** | Grounded Q&A over exactly one share link's guides: a guest asks, and gets an answer drawn only from that shared content, with citations — or an explicit refusal. | **Built by Prompt 7, unproven** (`docs/platform/ASK_PLAYBOOK.md`): migration `20240129_ask_playbook`, `ask-playbook`/`embed-guides` edge functions, `AskPlaybook.jsx`, eval set. Nothing deployed; flag `VITE_ENABLE_ASK_PLAYBOOK` off. | Supersedes `SPEC_ASK_PLAYBOOK.md` (branch `claude/spec-ask-playbook`). The refusal — *"I don't see that in this playbook"* — is a **first-class product state**, not an error. |
| **Alfred** | The host vertical's name for **Ask the Playbook** — the guest concierge on a property's guest guide link ("what's the wifi?" at 11pm), plus the planned owner-side digest of unanswered questions (Prompt 18). | The *same* `ask-playbook` function and the same scope resolution; only the copy differs, sourced from workspace data like `content_categories` and `workspace_roles.label`. | **Not a second system.** A property's guest link is already a bundle share, so Prompt 9 gets the guest VA with no new endpoint. Writing it as a fork would have meant building retrieval, grounding and rate limiting twice. |
